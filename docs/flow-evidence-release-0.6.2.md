## 根因与修复

**交接与检索。** 旧检索账本按整个用户轮次和查询文本汇总。退款和无知识库答案事项可能共用查询，旧记录无法表达一条调用由哪个事项发起。现在调用方可填来源中的 `item_ref`，运行时只根据实际配对的调用与结果分别统计执行状态。未指定标识的调用单列；账本仍有 900 字符上限，超出时显示遗漏数。标识由模型填写，复核时仍需阅读查询及来源。已有模板和结构化、普通上下文两种模式都能收到新的来源核验提示。它要求引用前核对原文、区分客户表述和推断、将证据不足的项留待核实。专项用例在旧实现上先失败，随后覆盖同一查询跨事项使用、未关联、无效标识和预算截断。

**Windows 配置。** 原生基线为 7 failed、16 passed，涉及行尾、权限断言和创建文件符号链接。原渲染器在记录尾部固定写 LF，第二次同步可能再次替换文件。新实现从解析后的记录边界选择布局，保留值内的 CRLF。测试还发现以“全文是否含 CRLF”选择布局会被新增多行默认值误导，该输入已加入回归。POSIX 继续验证 `0600`。Windows 对新临时文件在创建时设置受保护的私有 DACL，刷新后原子替换，并对已合规文件验证重复同步不替换。Windows 原文件符号链接的夹具和拒绝断言保留。

**安装包。** 从修复前源码实际构建 Frontend wheel 后，独立解释器找不到 CLI、Web、Qt 共用的 `agent_frontend.runtime_loop`。可编辑安装直接读取源码，掩盖了遗漏。现在将模块列入 wheel 文件清单，并在 PR 的 Linux 工作流里从实际 wheel 导入并创建、关闭事件循环。

## 真实模型复验

在 Windows 独立验证目录中使用用户已有连接，保留 Windows 系统代理、原模型、设计助手 xhigh 生成的冻结模板和节点 medium/auto。每轮都从空项目状态开始，使用已授权的 32k 输入窗口、4,096 输出预留、90 秒模型调用、30 秒确认及 1,800 秒 Flow 期限。没有重新设计模板，模拟业务动作仅写入临时项目。原 QA 脚本 SHA256 为 `f7364f209e1dc75cc9fe756f94a9f16e3e7bd29087a2acec103482adbd18fd7d`。

**第一轮，`4e59074`。** 五个节点在 804.126 秒内完成并排空，主模型 35 次调用，42 对工具记录，8 条模拟写入与工具参数相符。冻结 QA 为 20/20，两项旧 P3 通过，逐句核对未见 B-03 或 B-05。但 B-04 仍然失败。退款实际检索两次，其中一次超时。无知识库答案事项实际检索两次，都正常返回。四次调用都填写了与真实问题对应的 `item_ref`，服务节点却在发送回复时写成该事项检索三次，人工节点沿用了三次且含超时的说法。不同工单的调用加起来没有超出原限额，错误发生在归属和表述。该轮业务总验收未通过。

旧观测器没有保存真实请求中的账本段。由该次会话重建的有界账本包含两个完整事项和四个查询分组，逐调用明细受 900 字符限制省略。重建不能证明模型实际收到了哪条提示。后续修复把机器计算的事项计数附在每个 Flow 检索结果后，兼容普通及结构化上下文。原始结果正文保留，执行状态和审计来自真实工具；有正文区间的结果重新校验摘要。对照用例先失败，再验证两种上下文、同批并发成功及超时、未关联及不完整配对。

**第二轮，`746f06c`。** 五节点在 750.566 秒内完成并排空，33 次主模型调用成功，40 对工具记录匹配，8 条模拟写入与参数相符。原 QA 20/20。服务节点生成无答案事项回复的第 11 次真实模型调用入口，确实包含该事项先前一条、随后两条成功请求的回执，系统汇总也正确区分了退款两次和无答案事项两次。这一轮四次查询均成功。服务回复没有虚报三次，人工交接正确写了两次。这里只采集消息角色、请求序号、回执数字和摘要，没有保存请求正文。原两项 P3 逐项复核通过。原关键字筛查仍给出两个阴性候选，复核依据是实际工单内保留了开票自述且仅核实系统状态，模拟交接明确没有真人接单。

这一轮仍有两项业务失败。技术节点第 3 次输出给运维的诊断把“网络环境”列为客户明确未记录，原反馈只提到页面、时间和设备。把网络环境列为下一步调查问题本身合理，误差发生在对客户原话的归属。服务节点第 8 次输出将退款申请人扩大为财务管理员。实际检索同时返回了退款和开票资料，退款条款只允许租户所有者发起，财务管理员出现在开票条款中。退款资格、期限和路径正确，实际未生成额外人工事项或外部动作。B-04 在本轮通过，整体语义验收没有通过。两轮的本机负载不同，耗时不作提速比较。

**第三轮，`c03780f`。** 增加同一条款核对动作、主体和条件的提示，并要求区分资料缺失与调查建议。五节点 732.346 秒完成，32 次实际模型调用、37 对工具记录、8 项模拟写入和参数一致，原 QA 20/20。外部人工接手及已开票自述这两项旧 P3 通过。CF007 没有捏造报表导出，也没有再将网络状况列为客户明确未记录。退款检索实际 1 次，无资料事项实际 2 次，B-04 通过。

仍有两项确定失败。人工节点第 5 次模型调用提交的 `reason` 表述成客户明确提出人工诉求。客户明确表达的是不要重复自动步骤，Flow 决定转人工有流程依据。该次请求已包含实际文件回执里的原反馈。服务节点第 6 次调用给退款客户写了一步未获条款支持的角色授权前置操作。该请求同时收到了退款及开票条款，退款办理人的主体已写对。证据表明额外步骤没有退款条款依据，无法确定模型为何写出它。两项均可定位到调用动态工具前生成的参数。另有一处“未提供部署环境”与同一记录中已知的离线私有部署描述并存，列为范围表达歧义，需要指明缺少哪种规格。

该轮不通过整体业务验收。运行后分别核验了 Windows 端 516 份受检文件和 WSL 端 486 份源码的运行前后摘要。两端 97 份 Core 直接字节一致，另有 13 份非 Core 文件存在既有 CRLF/LF 差异。首次附加跨平台原始字节预检因此停止，未发出模型请求。独立保存两端原摘要后，以明确的行尾归一化核对跨平台文本，再按每端原始字节冻结运行内容。

## 提交草稿前的来源复核

第三轮已经证明原反馈和检索条款进入了出错的那次请求。用户选择保留自然语言表达，增加同模型独立复核。实现于 `adf2761`。Flow 在动态工具提交前、节点交接发布前筛选客户明确意愿、权限及办理条件等有来源风险的说法。复核使用同一配置与推理强度，从当前轮实际执行并完成的内置读取、检索回执中提取完整可验的正文区间。运行人直接输入的范围由框架标记并核对摘要。上游自述、其他会话、未配对结果或历史检索都不能充当原始来源。每次独立复核只接收草稿和有界的来源数据，不开放工具。费用、并发槽位、轮次与请求时限沿用节点原设置。

模型必须返回明确的审查结果。返工意见包含字段、理由和可在指定原文逐字核验的短引。错误格式、无法核验的引用和复核故障均不能放行。被拒动作保留实际调用及未执行回执，重新表述同一事项仍需复核，收到真实成功回执后才解除待办。还有未解决的争议写入时，节点进入检查点。终稿修订最多两轮，禁止重复写入，缺少来源时可用原授权补读一批。此机制检查模型给动态工具的参数和交接，不分析任意工具代码执行后的全部行为。对自然语言含义的判断由模型完成。

离线专项用受控回调及真实临时文件验证入口、否决、修正和落盘。接入前观察到 8 项产品失败。专项还覆盖旧会话重复使用调用 ID、来源去重、跨事项隔离、改写后再审、错误的工具调用、网络错误、取消和预算耗尽，共 73 项通过。后续补充的部分用例首次运行时共享源码已更新，其结果记录为覆盖验证。

全量回归还找到了一个计数错误。原格式修正用例故意让第二个请求的输入超窗，服务商实际只收到第一次请求。初版在检查窗口前就预留轮次，`model_rounds` 错误地记为 2。Linux 全量为 1 failed、3,022 passed、76 skipped、5 deselected（229.04 秒）。在独立工作树复现原断言后，把记账移到上下文、持久化和取消检查完成之后，再调用服务商。原断言和窗口保持，格式修正及草稿运行专项 45 项通过。修正提交为 `1f2cb6e`。

**第四轮，`adf2761`。** 五节点流程在 274.054 秒排空，但第一节点失败，另外四节点被阻断，原 QA 3/20，没有发生业务写入。分流工具已成功返回全部 7 条反馈。最初的审查器只接收内置文件和检索的来源，它看到的是 530 字符的工作区说明和 120 字符的运行指令，反馈正文覆盖 0/7。前两次审查各列出 4 条字段意见，8 条引用都能在它所见的两份资料中逐字找到。引用格式有效仍不足以说明拒绝合理。三个候选稿把 7 个事项分到了原任务要求的分支，审查者却缺少用来核对这些记录的正文，也没有看到节点自己的分类和路由规则。此次失败保留，模型提供了实际用量，配置没有价格时费用金额记为未知。

`f552a4f` 补上两项来源。对于节点实际执行的选择型动态工具，运行时核验本轮唯一配对的调用、成功退出和完整 JSON 输出，并以“工具实际返回的数据”交给复核者。它只接受相对路径和简单选择参数，保留路径的来源，排除带写入正文的调用及常见写入回显，仍优先保留第一方文件和检索数据。这个标记不能证明任意 Python 工具只读，也不能证明某人身份、外部已执行或政策授权。节点当前职责单独提供，能够解释“为什么按流程转人工”，不能证明“客户明确要求转人工”。当现有来源无法回答问题，复核者可以指出应补读哪种资料，不必给不存在的依据编造引文。

## 同一模型原始草稿定点对照

使用真实模型、原配置和原 90 秒调用期限，对三个独立的原始草稿发起付费复核请求，每次均不开放业务工具。这是定点回放，不是五节点全流程复验；以下结果不能称为全流程成功。

- **A：** 实际完整反馈分类 7/7，提供 3 份来源，其中包括低信任的动态读取结果。请求在 90.013 秒超时，累计推理 19,453 字符，没有可见判定，也没有精确 usage。不能据此断定超时原因，本次没有重试。
- **B：** 88.433 秒，提供 4 份来源，返回 revise，1 项意见的引用逐字可核验。它正确拦住了“客户明确要求人工”：原反馈只表达旧自动帮助无用。
- **C：** 85.938 秒，提供 11 份来源，返回 revise，2 项意见的引用均逐字可核验并与草稿字段匹配。两项均为真实错误：一项指出额外退款授权步骤缺少条款依据；另一项指出原反馈只述首次购买时间，草稿却写“按您提供的付款时刻推算”，而退款政策从首次付款起算。购买与付款时刻不能自动等同，应表述为假设或等待订单核实。

另做纯离线来源投影实验，A、B、C 的字符数分别为 1,863→1,863、991→991、822→822，均无缩减收益，因此舍弃该实验。离线投影不是模型请求，也不能作为业务验收结果。

## 逐句复核与可核验引文（第五至第十轮）

- 在临时项目中，先提交含争议句的草稿，独立复核退回；节点修改并取得批准，在下一轮用原名、同一组参数正式提交。预审阶段写入量为零，最终实际业务文件只有一条记录。
