# 客服反馈分流与 Working 实测（2026-11-10）

> 文档类型：历史验证报告 · [Working 使用指南](agent-flow.md#working-运行视图) · [原客服分流用例](agent-flow-customer-service-validation-2026-11-02.md)

## 验收计划

1. 从原客服夹具复制合成反馈到独立工作区，保留「垃圾、技术、服务」分类与技术转模拟运维、服务检索后初答、自动帮助无效转模拟人工的路径。预期结果留在操作者一侧。
2. 让分类节点调用 `create_session` 分派至少两个子任务，调用 `wait_agent_task` 收集结果，再交给下游。记录实际模型请求区间、子任务并发峰值、节点耗时及端到端耗时。
3. 用 Chromium 打开真实运行的 Web Working。使用同一运行的只读快照核对 Qt Working 面板，并单独验证桌面应用的运行桥接。核对任务概要、模型、状态变化、子 Agent 数量、右栏详情和结束后实例移除。
4. 对发现的问题先复现，再复测。工程回归与真实模型的业务结果分别计量。

选取原夹具中的六条反馈 CF-001、CF-002、CF-003、CF-004、CF-007 和 CF-008，覆盖 P1 和 P3 技术问题、常规退款问询、自动帮助无效的发票问题、广告和提示注入。保留分类、技术初判、服务初答、模拟运维和模拟人工五个节点。测试运行使用 WSL2 Ubuntu 26.04.1、Python 3.12.14、2 个子任务并发槽和 4 个模型请求槽。

## 实际运行与性能

三次执行均调用同一个真实 DeepSeek Flash 服务。检索使用隔离的八份政策及校验过的 BGE 和 mMiniLM 模型文件，下载时间单列。下表的重叠为客户端实际模型请求区间交集，各行只有一轮且提示词有差异，不能据此推算服务端并发或性能提升。

| 运行 | 结果 | 端到端 | 成功模型请求 | 两个子 Agent 请求重叠 |
| --- | --- | ---: | ---: | ---: |
| 首轮 | 分类交接失败，四个下游节点阻断 | 23.151 秒 | 9/9 | 3.737 秒 |
| 第二轮 | 分类与技术通过，服务交接失败 | 72.635 秒 | 19/19 | 5.392 秒 |
| 第三轮 | 五个节点和五份交接全部通过 | 151.174 秒 | 29/29 | 4.631 秒 |

第三轮各节点会话耗时依次为 43.483、17.803、37.489、20.096 和 32.130 秒。两个子任务从创建到完成分别为 4.784 和 5.899 秒，子 Agent 模型请求峰值为 2，包含主节点在内的请求峰值为 3。七个会话共记录 31 个完整工具调用与结果对。一条真实客服知识库检索耗时 10.895 秒。Working API 每 250 毫秒采样一次，捕获 185 个变化快照，覆盖全部五个节点、两个子 Agent 同时活跃及结束后实例移除。无令牌请求返回 401，授权请求返回 200。

第三轮六条工单的独立检查为 **52/53**。两条技术反馈按 P1、P3 交给模拟运维，广告和提示注入未进入业务分支。CF-004 保留发票标识与原编辑入口不存在的失败经历，直接转模拟人工，未调用 RAG。CF-002 引用了实际检索返回的 REF-01，初答遗漏 REF-02 的申请路径和材料。

随后只复跑服务节点，保留同样的六条输入、知识库和已核验的上游分类，要求对可自动初答的工单查实办理入口、材料和引用。定向复验耗时 44.467 秒，通过 **20/20** 项检查。CF-002 给出完整路径、材料和仅提交审核的边界，REF-01、REF-02 均能匹配实际检索。CF-004 仍直接转模拟人工且没有检索。该复验未重新运行五节点，整轮结果仍为 52/53。

## 两端 Working 观测

- 首轮 Chromium 在 1440 × 900 确认悬停、选择分类节点、模型与任务概要以及两张子 Agent 详情卡。节点结束后实例移除，宽屏截图只保存到空态，选中时的结果来自实际 DOM 观测。
- 第二轮 Chromium 在 416 × 800 确认两张子 Agent 卡、完整可见的悬停提示、详情下移和无横向溢出。抓取的窄屏悬停图显示技术节点仍在运行时，已完成的分类节点显示 0 个活跃、共 2 个子 Agent。
- Qt 离屏面板读取同一已授权的实际运行快照，观察到阶段变化和两个子 Agent，核对宽窄两种布局、任务概要、模型及右栏详情。桌面应用的原生 RuntimeBridge 另跑受控模型回归 2 项。两端只有读取观察器，运行状态由一个 Core 写入。
- 第三轮由认证 API 采样确认完整生命周期。两端实际界面验证取自前两轮，未将第三轮的 API 样本计作新的界面截图。

## 发现与修复

首轮实际执行在 23.151 秒后因分类节点交接失败而停止。分类节点把契约说明中的 `fields` 当作输出外层，未在顶层输出约定的 `artifact` 和 `ids`。Core 返回 `fields_mismatch`，阻断剩余四个节点。分类已真正委派两个子 Agent，两者的模型请求重叠 3.737 秒。该轮九次模型请求均成功。

第二轮修正了分类节点的格式示例，但服务节点把业务结果写到聊天正文，未调用文件工具，仍因 `fields_mismatch` 阻断两个下游节点。第三轮在测试指令中明确要求先用文件工具写产物并读回验证，再返回只含产物路径和 ID 的交接。三轮均使用新工作区和相同契约，保留原有业务断言。

Working 原先用 Flow 节点和委派队列的 `running` 显示状态。节点调用委派工具等用户批准时、子 Agent 自己等高风险操作批准时，两个位置都仍显示「运行中」。新增用例通过真实确认机制复现两处偏差，拒绝了子 Agent 对临时夹具的删除请求并核对文件内容。

修复后，进行中的节点和子任务采用对应会话的排队、等待确认或停止子状态，队列终态和实际审批规则保持原样。回归先得到两个 `running`，修复后均为 `confirming`。此项用受控模型驱动，审批、工具路径和文件断言走实际 Core。

发布复核还复现了子 Agent 的独立后续输入覆盖原委派模型与阶段、取消排空期间提前显示终态，以及默认子任务标题截断后留下凭据前缀。现在委派读数绑定其会话轮次，取消排空期间仍显示「正在停止」，自动标题先脱敏再截断。运行时模型连接的推理显示使用该连接的语义，空设置交给服务默认。

复核也复现了 Web 刷新返回 503 后把上次快照继续显示为实时，以及请求长期未返回时，离开再进入仍停在加载中。现在保留的快照会明确标记过期。请求 10 秒超时并自动重试，离开 Working 会取消当前读取，重新进入时请求新快照。Chromium 受控回归核对了 503、超时、恢复、选择与滚动位置，以及隐藏时停止请求。
