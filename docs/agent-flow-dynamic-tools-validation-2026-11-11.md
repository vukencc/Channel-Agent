# 客服反馈分流与动态工具实测（2026-11-11）

> 文档类型：历史验证报告 · [Flow 使用指南](agent-flow.md) · [原 Working 客服用例](agent-flow-working-validation-2026-11-10.md)

## 计划与证据边界

本次以真实配置的 DeepSeek V4.1 Flash 调用设计助手，重新生成五节点客服 Flow 及可执行工具；没有手写工具代码冒充模型生成。随后在独立项目中通过实际 Core 调度、真实文件 I/O 和真实本地 RAG 运行，界面检查与受控工程回归分别记录。

沿用原冻结夹具中的 CF-001、CF-002、CF-003、CF-004、CF-007、CF-008 六条合成反馈，覆盖紧急导出故障、信息不足的卡顿、退款初询、此前自动帮助无效的发票问题、广告及提示注入。金标准由原三十条夹具取六条，只供独立验收，不进入项目、模型提示或知识库。不能把六条专项结果称作三十条全量业务通过。

五节点及职责为：分类 → 技术初判 / 服务初答 → 模拟运维 / 模拟人工。分支仍按拓扑串行执行，各节点根据上游分类筛选自己的数据。测试选择 sandbox 与 full_access，节点只公开必要文件工具和专属业务工具，服务节点单独启用 RAG；没有向模型公开通用命令、网页、环境或委派工具。专属工具通过部署允许的既有命令能力运行，不改变隔离、确认、审计或工具结果配对。

| 节点 | 模型生成工具 | 实际职责 |
| --- | --- | --- |
| classify | `read_feedback` | 读取项目 feedback.json 完整对象，分类并写产物 |
| service | `send_ai_reply` | 将初答写入 delivery/ai_replies.jsonl，按 ID 幂等，冲突报错 |
| human | `submit_human` | 将人工交接写入 delivery/human_queue.jsonl，按 ID 幂等，冲突报错 |

两种 delivery 文件是合成业务接收端的本地模拟记录，不证明外部消息送达或真人受理。技术与运维节点只分析并制作排查计划，不操作生产系统。所有业务输入与八份政策只读，使用唯一新临时工作区；用户原项目、会话、知识库和客服模板保留。

执行步骤：真实设计 → 审阅代码/权限与便携格式 → JSON 导出重导入 → 新建独立项目 → 完整整图运行 → 原始会话与产物交叉验收 → 两端工具详情/文件往返 → 修复及工程回归。每次整图复验新建空工作区，不复制上轮成功输出，不追认旧失败。

## 已发现问题与修复

1. **生成图重叠。** 实际 Chromium 只显示最上层节点，其他节点不能点击。Core 仅对新设计省略坐标或全部重合的情况进行确定的拓扑分层布局；明确的不同坐标保持不变，普通 JSON 导入不改布局。缺省和全重合两个回归先失败后通过，并验证原坐标保留。
2. **交接提示混淆配置层与结果。** 首轮模型将内部 fields 配置层当成输出层。Core 将约定转换为标准 JSON Schema，明确结果的顶层字段。第二轮仍有运维节点最终返回普通说明，因此把同一约束同时绑定到节点系统提示与本轮输入，新建、复用路径一致。后续真实轮次表明这些提示改进不能保证模型格式可靠，失败仍如实保留。严格验收、失败阻断和原子保存规则保持，不自动改写模型输出或把未通过的节点标为完成。
3. **Working 悬停层挡住相邻按钮。** 实际浏览器从人工节点悬停后点击服务节点等待超时。提示层改为不接收指针，补先失败回归，并用实际浏览器重复该点击路径核对。
4. **新验收器误解命令结果协议。** 初版受控 fixture 错误要求成功结果包含空 stderr 标记；生产只在 stderr 非空时附该段。真实动态工具记录揭示误拒收。现在按实际 exit 0/stdout 协议解析完整 JSON，仍拒绝非零退出、stdout 污染、stderr 诊断、多份 JSON、重复键和非有限数值；这是测试代码问题，未更改生产工具输出协议。

5. **Windows 验收路径分隔符。** 原生专项有 69 项通过、1 项失败，文件白名单把反斜杠相对路径当作额外产物。改用 `Path.as_posix()` 规范化比较，原断言不变；同一原生专项复跑 70 项全部通过；加入转人工空 reply 的正反回归后最终 72 项通过。

6. **新验收器要求转人工记录仍生成自动答复。** 当前岗位约定在自动帮助已失败时直接转人工、不再自动回答，因此 handoff_human 的 reply 可为空，确认语由人工节点 acknowledgement 验收。新增空串正/反例先失败后修复，仅 initial_reply 保留非空且与实际发送相同的要求；原三十条历史验收器不改。

独立证据导出初版还把 Core 会话的 idle 当作 Flow 节点终态。修订为对照权威 Flow 的 completed，并单独要求原始会话 idle；不是修改运行状态。首版导出误判结果保留，223/224 为修正导出和岗位契约后的第六轮结果。

7. **设计模板漏保留必要类别和分级规则。** 只列 technical/service 标签不足以表达原业务边界；同时优先级提示遗漏“轻微/待澄清 P3”。以原场景规范逐项对照补齐，保持分类、优先级金标准及模型生成的工具代码不变；不将“客户说帮我看看”自动当作服务咨询，也不将信息未知等同更高等级。

业务配置修订分别保留 `template-review-patch.json`、`template-priority-review.json` 和 `template-business-contract-review.json`，可核对来源、修改字段与工具定义不变。对初答错误角色、客户经历推断和等级漂移的修订是业务规则提示补全，不是对模型任意输入可靠性的保证。

## 复用模板与剩余限制

[可导入的便携模板](../src/agent_test/scripts/cases/customer_feedback_dynamic.template.json)来自真实设计助手工具实现及上述明确记录的业务规则修订。最终 v5 已在 Web 和 Qt 实际导入、保存/导出、重导入，按五个省略的 handoff_contract:null 补齐后与完整 Core 模型逐字段一致。导入不创建工作区、知识库或模型连接；需自己选择项目、准备 feedback.json 和 support 源。两份 delivery 只在该项目内模拟业务接收，未发送外部客户消息。

**结构化 Handoff 的格式可靠性仍未通过本次真实模型验证。** 提示改进不能保证模型遵守，服务商能力声明和小探针也不能代替整图验证；前五轮失败保持。成功结论对应产品原有的默认文本交接路径，五份业务 JSON 仍接受完整独立验收，没有剥离或自动修补不合格的结构化输出来算通过。
