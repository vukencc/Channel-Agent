# Agent 系统诊断与修复报告

日期：2026-09-27。基线提交：`7f8461e`。测试模型：当前配置的 `deepseek-v4.1-flash`，通过 OpenCode Go 网关调用。

## 结论

本次问题由多个环节叠加：命令执行器错误处理多行脚本并继承终端输入、模型长时间思考、过短的流空闲超时，以及 SDK 首次加载阻塞事件循环。不是单纯增加线程或内存就能解决。

修复后，实际失败场景的完整绘图任务连续三轮成功，最终代码再次复验成功；文件确实落盘。完整工程回归 **128 项通过、2 项阈值相关测试未执行**。没有以缩减测试输入替换原始故障场景，也没有硬编码模型回答。

## 1. 命令超时与终端输入争抢

**证据：** 用户日志记录 16:47:53 执行 `python3 - <<'EOF' ... EOF`，16:48:03 超时。旧实现使用 `shlex.split` 加 `shell=False`，没有解释 heredoc；Python 收到 `-` 后等待标准输入，而输入又继承自 CLI。正常代码和语法错误都不能及时返回。

**实验：** 用保持打开的输入管道模拟交互终端，分别运行正常 heredoc、裸 `python3 -`、含非法元组形参的脚本，各重复三次。旧版 9/9 达到人为设置的 0.5 秒时限；该短时限只用于快速复现等待输入，并非原始用户的 10 秒配置。

**修复：** 宿主仍以 `shell=False` 启动 Bubblewrap，仅在隔离环境中执行 `/bin/sh -c`。标准输入连接 `/dev/null`，保留确认、审计、网络/文件隔离和超时进程组回收。支持 POSIX 管道、重定向和 heredoc。

**复验：** 正常脚本三次为 0.017 / 0.010 / 0.010 秒；错误脚本在 0.026–0.035 秒返回 `SyntaxError`。重放日志中的完整原始命令，0.049 秒返回真实语法错误；仅将元组形参改为合法 Python 3 写法后，0.012 秒完成计算。执行器不会替模型伪造修正结果，提示词也明确要求 Python 3 语法。

相关实现：`tools/command.py`、`tools/sandbox.py`、`core/agent.py`。

## 2. 思考配置失效与思考模式协议缺失

**证据：** `.env` 中的 `REASONING_EFFORT` 原来未被加载或发送；流中的 `reasoning_content` 被丢弃。

**修复：** 接通思考强度，并增加明确的 `THINKING_MODE=auto/enabled/disabled`。关闭思考时不同时发送强度参数。启用思考时，将服务商返回的推理字段保存在私有会话 JSON 并用于后续请求，不显示或写入普通诊断日志正文。

[DeepSeek 官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)要求携带工具的后续请求回传推理字段。旧代码存在这一协议缺陷，但现有证据不能证明用户原始失败就是由它引起；本次直接复现的故障是命令与读取超时。

**实验：** 先对普通保存任务和较简单绘图任务做三组原请求/低强度交错对照，共 12 次真实首轮请求。简单绘图的首个可见输出从 11.916 / 47.210 / 22.101 秒变为 3.109 / 2.800 / 3.522 秒。然而原始双人物绘图任务在低强度下仍失败，说明首轮数据不能代表端到端成功率。

**实际配置：** 已将本地 `.env` 调整为 `THINKING_MODE=disabled`、`REASONING_EFFORT=low`；关闭思考时后者不发送。默认快速模式适用于当前文件/网页任务，不等价于高强度推理质量。复杂推理任务可显式恢复 `enabled`；其他服务商不支持扩展时使用 `auto`。没有更换模型。

## 3. 流空闲时限错误与缺少总时限

**证据：** 原会话末尾为 `ReadTimeout`。关闭思考后，三次绘图仍在开始回复后的约 15 秒断流。放宽空闲时限后，同一任务测到最大流帧间隔 29.931 / 34.170 / 36.770 秒；最终复验为 47.314 秒，随后返回完整的大工具参数。

**根因：** 当前服务链路在生成长工具参数时出现较长数据空档，15 秒空闲时限会提前切断正常请求。这是实测的流行为；仅凭客户端记录不能进一步断定网关内部缓冲的具体实现。

**修复：** 空闲时限改为 60 秒，同时新增 90 秒单次模型调用总时限，覆盖建立连接、重试等待及流接收；默认最多尝试 2 次。两者不是整轮任务时限。遇到已输出内容后的断流不自动重放，避免重复副作用。错误信息包含实际已等待时间及两种时限。

结束原因缺失、`length` 截断、无效工具 JSON、缺失/重复工具标识均禁止进入工具执行；取消或失败仍保存已收到的正常文本。

**端到端实测：** 使用用户实际失败的“双人物在田野骑自行车，HTML+CSS 保存为 index.html”任务。除末次 SDK/UI 修复外，各组使用相同任务和模型。测试工作区为空且相互独立，测试确认自动批准；耗时不包含人类阅读确认的时间。

成功生成的 HTML 分别为 18,395、16,497、18,749、25,171 字符。最终复验首个可见输出为 2.314 秒，完整工具参数在约 51.6 秒时收到。因此不能宣称复杂绘图已经“秒完成”；主要余下等待来自远程生成。

每组还执行两个并发会话，实际创建同名 `hello.txt` 并调用工具读回：共 8/8 成功且工作区隔离。最终两个会话分别 9.916 / 10.363 秒完成。

相关实现：`config.py`、`core/llm.py`、`core/sessions.py`。

## 4. 本地 CLI 冷启动卡顿与等待不可见

**证据：** 真实任务首次调用的事件循环心跳曾延迟约 263–301 毫秒。使用真实 SDK、模拟 HTTP 响应隔离网络因素，三次新进程实验中，旧调用方式最大事件循环间隔为 248.40 / 189.15 / 181.50 毫秒。

**修复：** 将 HTTP 客户端创建和 SDK 延迟资源导入放入工作线程，以锁保证多个 Agent 共用单个客户端。流式文本和参数在模型层使用分片列表拼接。CLI 显示接收字符数；长时间无数据时显示等待时间与空闲上限，区分本地工具执行和模型等待。

**复验：** 同条件 SDK 实验降至 16.63 / 17.37 / 17.07 毫秒。最终真实绘图的最大心跳间隔为 61.83 毫秒，两个并发文件任务约 12 毫秒。心跳与模拟 HTTP 指标不等于真实终端帧率；终端键盘输入/退出另由 pytest 驱动验证。

相关实现：`core/llm.py`、`core/sessions.py`、`core/cli.py`。

## 5. 命令大输出导致内存膨胀

**缺陷：** 旧实现 `communicate()` 收集全部 stdout/stderr 后才截断展示，输出很多时 Agent 内存会随之增长。没有证据说明用户这次短计算脚本已触发该问题，但这是确认存在的资源风险。

**修复：** 用 `selectors` 同时持续排空两条管道，仅保留有界 UTF-8 前缀，并标明截断。超时或取消时仍清理进程组。

**复验：** 真实子进程同时产生 stdout/stderr 各 10 MB，正常退出；每流展示上限 1,000 字符的测试中，捕获路径 Python 分配峰值小于 1 MiB。该限制针对 Agent 捕获缓冲，不是对子进程内存、磁盘或 CPU 设置配额。

## 6. 可选 RAG 评分阻塞继续对话

**缺陷：** 用户实际开启 `RAG_ASSESS`。旧实现回答后同步等待评分，单次可等 120 秒且最多尝试两次；所属会话一直处于忙碌状态。原始绘图没有调用 RAG，所以这不是该次绘图故障的直接原因。

**修复：** 评分改为后台任务，独立 30 秒总时限、不自动重试。用户可立即继续同一会话，新一轮取消旧评分；通过轮次标识防止旧结果覆盖新对话，退出时取消并保存状态。

**复验：** 注入缓慢评分、评分超时以及继续下一轮，验证回答不被阻塞、失败不改变回答、旧评分不串轮。保留评分功能，没有通过删除它获取性能改善。真实本地向量 → BM25 → RRF → 重排链路工程测试通过，未重新做搜索阈值或全量质量评测。
